# Scopework 0.13.0a

**Comparison range:** `v0.8.0..v0.13.0a` (the tag is placed on the package commit). This is the first release under the Solarity convention ([proposal](../proposal-versioning.md)):
- a product version with a stage suffix;
- a reserved build number;
- release notes that account for every commit since the previous version change.

**Why 0.13.0a and not 0.9.0.** The version path was recalculated from 0.1.0 with SemVer's pre-1.0 rule: a minor bump for new features or breaking changes, and a patch bump for fixes only. Several earlier releases were numbered as patches although they added features or changed the catalog format. Applied consistently, 0.8.0 would have been 0.12.0, so this release is 0.13.0. The derivation table is in [TODO.md](../../TODO.md) under the versioning item. Published tags and changelog headings stay as they were. Alpha: the product is pre-1.0 and its interfaces are still moving.

**Upgrading.** The MSI version is now `major.minor.build` (this package: 0.13.1, for Build 000001). It sorts above 0.8.0, so installing over 0.8.0 upgrades in place. The UpgradeCode, the executable names and the research home are unchanged.

## What changed

### Several agents at once: the coordinator

- **One coordinator per research home** serves the CLI over a same-user named pipe.
  - It starts on demand and exits when idle.
  - It closes gracefully for Windows shutdown and installer upgrades.
  - Direct mode and older versions stay correct beside it.
  - `SCOPEWORK_COORDINATOR=off|auto|required` and `SCOPEWORK_SUBMITTER` control and name the caller.
- **Reads never wait for writes.** They answer from the last committed revision held in memory and carry `revision` and `pending`. A read that overlaps another process's commit or import publication is answered again under the lock, so no answer mixes two revisions.
- **Writes queue by class, with ageing.** Queued record operations merge into one commit and accept or reject exactly what they would one at a time; structural operations commit alone. A failing writer answers `writer_failed` and keeps serving.
- **Queue visibility:** `research queue`, `coordinator status` and `coordinator stop`. The dashboard footer and the Research records status bar show `Queue: n running, m waiting`.
- **Tool leases** (`research job run`, `job status`):
  - leases on named project resources, declared in `tools/coordinator.toml`;
  - same-key requests that wait together join one run, each getting its own result, and payload-less ones are covered;
  - several resources are granted together or not at all;
  - without a coordinator, lock files stand in.
- **Drift and audit.** Drift detection records changes to declared files outside a lease, and catalog or sidecar changes outside Scopework. `research tools audit` (advisory) compares what tools appear to use with what is declared.
- **Measurements for later decisions.**
  - Reads per record class are counted.
  - Commit measurements cover batch sizes, open, delta, journal and apply times, and queue waits.
  - Both are in `coordinator status` and in daily `coordinator-reads` and `coordinator-commits` history entries.

### Catalog and performance

- **Moves and deletions no longer rewrite unrelated reports** (`fix(catalog)!`). Quoted source strings keep their bytes, and moves read only the reports that mention a moved folder.
- **The annotation ledger** is repathed in place when the catalog commits, so journals no longer copy it. `node batch` reports moved paths, and `node resolve` maps old report paths to current ones.
- **A completion change reopens only complete records it reaches** (ancestors and prerequisite consumers). It no longer bumps every ancestor revision.
- **Commits are cheaper:**
  - in-process commits serialise the catalog once and skip re-reading their journal, about 200 ms to 112 ms on the live catalog;
  - the coordinator's writer keeps its catalog in memory between batches and reuses fingerprints: open 65 ms to 0 when reused, journal 134 ms to 62 ms;
  - one Solworker runtime serves each process.
- **Recovery:**
  - errors name the file and journal involved;
  - folder renames retry Windows sharing violations;
  - reads answer from the committed catalog while a pending transaction is blocked.
- **Locks queue fairly in arrival order.** Batch schema 2 checks record revisions instead of the project revision. `research journal --compact-sidecars` can reclaim large historical sidecar copies (opt-in, irreversible).

### Interface

- Secondary windows, dialogs and menus use the dashboard's classic style, and Research records follows the dashboard's project. Mark complete is a separate confirmed action that names what blocks it.
- `research --version` and `--build-info` report the product version, build number and source revision. The About dialog and the executables' version resources show the same identity.

### Fixes from the whole-app review

- Merged claim operations keep every claim and refuse conflicts.
- A failed merged commit leaves no uncommitted state for readers.
- `wait --idle` honours the coordinator's queue.
- Drift ignores sidecar creation and same-tick rewrites.
- Direct-mode resource locks remove their holder records.
- Non-ASCII case folding can no longer split a path.
- `TOKEN_USER` is read unaligned.

## Validation

- **Tests:** `cargo test --all-targets` passes on Windows, including the coordinator suites (`tests/coordinator.rs`, `tests/coordinator_leases.rs`). Each review fix has a regression test that fails without its fix. Exceptions: the alignment fix, and the debug fault hooks that widen race windows only in debug builds.
- **Lint:** `cargo clippy --all-targets -- -D warnings` and `cargo fmt --check` are clean.
- **Identity:** `tests/build_identity.rs` checks it against `Cargo.toml` and `BUILD_NUMBER`. The packaging run checks that the executable reports the reserved number before building the MSI.
- **Measurements:** taken on a copy of the live catalog (`wow-335a-12340`, 31,603 records), as recorded in the coordinator proposals.

## Known limitations

- **Project tools must adopt leases** before tool work queues or merges; the steps are in [CHANGELOG.md](../../CHANGELOG.md) under "Project tooling: action needed". The time target for merged ledger writes is unmeasured until then.
- **Not built yet:** faster fingerprints and the effective-status cache (phase 3, 3.3 and 3.4). They wait for about a week of live measurements.
- **GUI writes run in-process**, beside the coordinator; they wait at most one coordinator batch.
- **Conditional jobs and a GUI history view** are not implemented.
