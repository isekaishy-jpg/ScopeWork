# Scopework 0.14.0a

**Comparison range:** `v0.13.1a..v0.14.0a` (the tag is placed on the package commit). A minor release under the version rules in [docs/building.md](../building.md): it adds features (quarantine, project groups, the implementation tracker, the history window, renames that follow through, `project tidy`), so 0.13.1a becomes 0.14.0a.

The range also contains the 0.13.1a maintenance package (Build 000004, `7309e86`), which reserved a build number without changing the version.

**Upgrading.** The package upgrades 0.8.0 and every 0.13.x package in place; the UpgradeCode, executable names and research home are unchanged. Its build number is reserved when it is packaged, and its MSI version is `0.14.<build>`. The catalog format is unchanged. After installing, `research project tidy PROJECT` lists the empty files earlier versions left in record folders, and `--apply` removes them; run it only once every GUI in use is this version, because an older dashboard's **Open data folder** expects the empty `data/` folders.

## What changed

The full list is in the [changelog](../../CHANGELOG.md#0140a---2026-10-24); this is a summary by area.

### New

- **Quarantine** ([proposal](../proposal-quarantine.md)). A chunk or function can be taken out of research at the human's request or after a Claude cyber (safety) stop. It counts as complete everywhere, is never offered as work, and is sealed against structural changes unless a request carries `--directed-by` the human's instruction, which history records. Prerequisites on a sealed record stay free, so later work can build on it.
- **Project groups** ([proposal](../proposal-project-groups.md)). Related projects share one dashboard tab with a menu to switch between them (`research group`, or **Dashboard group** in Research records). Groups live in the home's `settings.json`, never in a project.
- **Implementation tracker** ([proposal](../proposal-implementation-tracker.md)). `research impl` and the dashboard's **Research | Implementation** tabs record a recreation: a free-form tree, research functions placed where they are implemented, implementation-only items and their completion.
- **History** ([proposal](../proposal-history-view.md)). Receipts record their commit time; `history show` filters by RVA and UTC day; `history kinds` lists the known tooling kinds; **View > Project history...** shows it in the GUI. Every catalog change now has a receipt, and import publications appear too.
- **Renames reach every citation** ([proposal](../proposal-rename-citations.md)). A batch rename rewrites every exact `` `OldName` (`VA`) `` citation in all reports and keeps the completion of reports changed only by renames.
- **Record folders hold only what is used** ([proposal](../proposal-empty-record-files.md)): no more `dep.toml`, `prereq.toml`, leftover import markers or empty `data/` folders, and `project tidy` removes the old ones.
- **CLI papercuts** ([proposal](../proposal-cli-papercuts.md)): prune explains its skips, `set-binary --expect-revision` amends an identity without reopening, readiness excludes Not Started records, and `status --ready-for-synthesis` lists parents ready for their synthesis.
- **Crash log** ([proposal](../proposal-gui-crash-log.md)): the dashboard writes `logs/gui.log` in the research home.

### Fixed

- **Dashboard memory no longer grows with every commit** ([proposal](../proposal-report-hash-memory.md)). The dashboard reached 50 GB on 2026-10-21; refreshes now reuse one thread's hashes and free replaced entries.
- **Commits have a definite outcome on Windows** ([proposal](../proposal-commit-outcomes.md)): sharing violations are retried for 20 s, then answered `commit_pending` instead of an ambiguous error.
- **Three code reviews of all of `src`** ([first](../proposal-review-fixes.md), [second](../proposal-review-fixes-2.md), [third](../proposal-review-fixes-3.md)), each by two independent reviewers, fixed among others:
  - batches, saves and context-only edits that reopened completed work they did not affect;
  - the seal: removals, reopens, status resets, prerequisite changes and an unreadable `quarantine.json` can no longer change sealed records without direction;
  - report-breaking record names, project names and binary identities;
  - coordinator waits, interrupted imports, pending-journal detection and post-panic snapshots;
  - dashboard refreshes that missed a commit, re-read every project, or reloaded every two seconds while a project was busy;
  - lock files left by commands on mistyped projects, and a CLI panic on a closed output pipe.

### Performance

- The dashboard refreshes only the projects that changed, and after a save only that project.
- Prerequisite validation is linear instead of quadratic, and no longer recursive.
- Completion throughput was measured: a member completion costs about 0.4 s, spent in project tools rather than the app ([findings](../proposal-completion-throughput.md)).

## Validation

- **Tests:** `cargo test --all-targets` passes on Windows (213 tests). Each review fix has a regression test that fails without it; the refresh race uses a deterministic hook instead of timing.
- **Lint:** `cargo clippy --all-targets` reports no warnings and `cargo fmt --check` is clean.
- **Not yet done at the version commit:** packaging, installing over 0.13.1a, and a run against the live research home. Record them here when the package is built.

## Known limitations

- **Policy questions left open** from the third review: whether reordering an architecture moves a quarantined chunk among its siblings, whether a directed import into a quarantined chunk keeps the chunk's stored status, and whether publication rechecks the seal. A possible false drift entry when an import lands is unreproduced.
- **Storage.** Each coordinator read clones the catalog (13.5 ms for the largest live catalog); the catalog and ledger are still whole files rewritten per change. Both belong to the storage backend design, which is researched but not designed (see `TODO.md`).
- **Tab overflow.** With many projects or very long names the dashboard's tabs can still run past the window's edge; groups reduce the number of tabs.
- **Effective status recursion.** Status evaluation still recurses through prerequisites of completed records; only a completed chain tens of thousands of functions long, far beyond any live project, would exhaust the stack.
