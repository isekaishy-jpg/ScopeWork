# Scopework 0.13.1a

**Comparison range:** `v0.13.0a..v0.13.1a` (the tag is placed on the package commit). A patch release: fixes only, so 0.13.0a becomes 0.13.1a under the version rules in [docs/building.md](../building.md).

0.13.0a was tagged, but its draft release was never published. 0.13.1a supersedes it, and the [0.13.0a notes](0.13.0a.md) still describe everything that came before.

**Upgrading.** This package is Build 000003, MSI version 0.13.3. It upgrades 0.8.0 and any 0.13.0a package in place; the UpgradeCode, executable names and research home are unchanged.

## What changed

A code review of 0.13.0a found five problems, and a second review of the fixes found three edge cases. Each fix has a regression test that fails without it.

### Coordinator and tool leases

- **Relative input files resolve in the caller's directory.** `--file`, `--body-file`, `--evidence-file` and `--diff-file` are made absolute before a command reaches the coordinator, including Windows drive-relative paths such as `D:body.md`. Previously the coordinator resolved them in its own directory, so a save could read another directory's file of the same name.
- **One exclusion mechanism for tool resources.** A coordinated `job run` also takes the per-resource lock files that direct mode uses, once its lease is granted. Coordinated and direct-mode jobs on the same resource can no longer run at the same time, in either starting order.
- **Reads cannot be fooled by a waiting writer.** The coordinator suspended its readers' checks for other processes' commits as soon as its writer started a batch, even while that writer was still waiting for another process to release the project lock. It now suspends them only while its writer actually holds the lock. Before, a read in that window could return another process's new report together with an older record.
- **Consistent job exit codes.** Every `job run` request exits non-zero when its own result is an error, whether it ran the command, joined another's run or ran without a coordinator. A payload with no result is answered `no result`.
- **Clean starts:**
  - the coordinator now starts without inheriting any of its caller's handles, so a script or test reading a command's output is never kept waiting by it;
  - its environment block is sorted as Windows documents;
  - if it cannot be started, `auto` falls back to direct mode instead of failing the command.

### Dashboard

- **Correct function totals.** "Functions in progress" and "Not done" count each function by its own effective status. Before, every unfinished function in an architecture was counted by its chunks' colour: one function in progress and one not started showed as two in progress. The README screenshot is retaken.

## Validation

- **Tests:** `cargo test --all-targets` passes on Windows. The new regression tests cover:
  - saving through a coordinator started in another directory, in `off`, `auto` and `required` modes;
  - coordinated and direct-mode jobs on one resource, in both starting orders;
  - a three-participant race: another process mid-commit, a coordinator writer waiting for its lock, and a coordinator read;
  - per-request exit codes for a holder, a joined request and direct mode;
  - the dashboard's function totals;
  - absolute argument resolution;
  - the environment block;
  - a detached child inheriting no handles.
- **Lint:** `cargo clippy --all-targets -- -D warnings` and `cargo fmt --check` are clean.
- **Packaging:** the run checks that the executable reports the reserved build before building the MSI.

## Known limitations

- **Tab overflow.** With many projects or very long names, the dashboard's project tabs can run past the window's edge; the tab strip does not scroll yet.
- **Unchanged from 0.13.0a:** project tools must adopt leases, two storage changes wait for live measurements, and GUI writes run in-process. See the [0.13.0a notes](0.13.0a.md#known-limitations).
